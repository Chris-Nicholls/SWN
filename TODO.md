- [x] Bug: Grids mode no longer functions at all
  - Confirmed real (not a bisection-build artifact): mode-switch flash fires, but total silence and the LED ring's playhead is frozen -- meaning grids_state.step itself was stuck, not just Grids-driven channels being quiet.
  - Root cause: DrumKitPreset's `grids_clock_divmult_id` field was added (22dfbe9) without bumping DRUM_PRESET_MAGIC ("DK01" unchanged) -- so an autosave/preset slot written by older firmware, before that field existed, still passes the magic check and gets loaded under the new, larger struct layout. The trailing field then reads whatever raw bytes happen to sit past where the old, shorter struct ended in flash -- on an erased/never-rewritten sector that's 0xFFFFFFFF, which as a float is NaN. `calc_divmult_amount(NaN)` -> `grids_clock_rate` becomes NaN -> `grids_step_phase += NaN` poisons it permanently, and `grids_step_phase >= 1.0f` against a NaN is false forever, so the shared Grids stepper never advances again. No crash, just silent + frozen. Every other field kept its original offset (this one was appended at the end), which is why nothing else looked broken.
  - Fixed by bumping DRUM_PRESET_MAGIC to "DK02" (src/drum_preset.c) -- see the comment left directly above it, including a reminder to bump it again next time this struct's layout changes. This makes every existing slot and the autosave sector read back as "not present" on the next boot (hard defaults take over instead of a differently-shaped blob), and everything re-saves cleanly under the new magic once a control is touched. Note: this does mean existing saved kits/autosave are invalidated by this fix -- expected and unavoidable given the corruption, not a side effect to work around.
  -> On the latest firmware: pattern-view LEDs now show correctly (they were being stomped by the TRANSPOSE/OCT display bug above, fixed separately), but the playhead still never advances -- same underlying symptom as before, on a build that should have had the magic-bump fix. Added a second, defensive layer directly at the point of use: update_drum_triggers() now sanitizes grids_clock_rate back to 1.0 if it's ever NaN/zero/negative/absurdly large, right before using it to advance grids_step_phase, rather than only preventing bad values at the one load path already fixed. Self-heals the global too, not just that tick, so it can't get caught again on every subsequent tick.
